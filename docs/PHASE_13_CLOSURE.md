## Production acceptance evidence

### Administrator password recovery

- `rcitcservices@gmail.com` is the only approved administrator reset recipient.
- Resend delivery is live from `noreply@rcitcs.com`.
- Reset links are single-use and valid for 30 minutes.
- Rapid reset requests are deduplicated to prevent a second message from invalidating the first recovery link.
- Recovery cookies use `Secure`, `HttpOnly`, reset-route path scoping and `SameSite=Lax` for mailbox-originated top-level navigation; normal authenticated administrator session cookies remain `SameSite=Strict`.
- The production reset flow has been manually accepted end to end: request → delivered email → verified recovery page → password replacement → reset token consumption → prior-session revocation → success redirect → sign-in with the new password → protected dashboard.
- The atomic `consume_admin_password_reset_token` RPC is service-role only and source-controlled through the forward-only corrective migration.

### Reliability / retry acceptance

The first production candidate acknowledgement exposed a transient pre-provider runtime failure that was incorrectly dead-lettered. Phase 13.7 treated that as a blocker instead of accepting eventual manual delivery.

A forward-only corrective migration now:

- schedules generic non-reset `EMAIL_DISPATCH_FAILED` infrastructure failures using the bounded 5m → 15m → 60m → 6h retry policy;
- leaves explicit provider retry timing authoritative;
- keeps administrator password-reset messages excluded from automatic retry;
- allows stale non-reset `sending` claims to be recovered after 15 minutes;
- preserves the maximum five-attempt bound;
- exposes only aggregate `stale_sending` health state.

Production proof reproduced the original failure mode deliberately. The first attempt was marked with generic `EMAIL_DISPATCH_FAILED` and no explicit retry time. The database assigned exactly a five-minute retry. The one-minute production cron later executed the due retry automatically with `attempted=1`, `succeeded=1`, `failed=0`; the message moved to `sent` on attempt 2 and Resend confirmed `delivered`. No manual requeue was used.

Idempotency replay of the same application event returned the original email-log UUID and left exactly one row for the idempotency key.
